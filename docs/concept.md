# pak256 構想のたたき台

2026-11-24 時点の下書き。決まったことではなく、決めるための論点の一覧。

## 1. 目的

- pak128・pak128.Japan の課題を解消した形で、統一された規格にまとめる。
- pak セットの権利を明確に管理し、作者の引退でメンテが止まる危険をなくす。
- 既存の pak セットとコンセプトを大きく変えず、遊ぶ人が移行しやすくする。

## 2. 確かめた前提

### 2.1 本体で 256px のタイルが扱えるか（OTRP の fork のコードを読んだだけ。本家 125.0.1 のコードと起動は未確認）

| 項目 | 結果 | 出典 |
|---|---|---|
| makeobj の大きさの指定 | `pak16` 〜 `pak32765` を受け付ける | `makeobj/makeobj.cc` 86 行付近 |
| pak の中の画像の形式 | 今の形式（版 3）は位置・幅・高さとも 16 ビット。読み込み側・描画側も 16 ビット。256px の幅を持てる（古い版 0〜2 は幅・高さが 8 ビット） | `descriptor/writer/image_writer.cc` 493 行付近、`descriptor/reader/image_reader.cc` 98 行付近、`display/simgraph16.cc` の `struct imd` |
| タイルの画素数 | 地面の絵の幅から決まる（pak の設定ではない） | `descriptor/ground_desc.cc` 398 行付近 |
| 高さ 1 段の画素数 | `tile_height` × タイル幅 ÷ 64。pak128 と同じ `tile_height = 8` なら 32px | `dataobj/settings.cc` 1929 行付近、`simconst.h` の `tile_raster_scale_y` |

**起動の試し（2026-11-24）**: pak128 を 2 倍にした pak で、OTRP v64 が起動した。メモリは pak128 の約 3.6 倍（64×64 の地図で 475MB → 1695MB）。起動の時間は約 3 秒 → 約 5 秒（粗い測定）（[記録](records/2026-11-24_poc-upscale-pak128.md)）。

描画は、同じ広さを見る比べで pak128 の約 2 倍の CPU を使うが、小さな街 9 つの地図では 1 コアの 5% ほど（同じ記録）。今の PC なら重さはあまり気にしなくてよい（2026-11-24、ユーザー）。

**未確認**: 物の多い地図での重さ、線路・車両などの絵のずらしが正しいか、本家 125.0.1 での起動。

フォーラムでは、256px のセットどうしを混ぜて使えるよう、pak256.Japan の縮尺に合わせることを勧める意見がある（2020 年）。pak256.Japan が Pak256-Ex の開発中の名前だったこととあわせ、検索結果の要約で読んだだけで、投稿そのものは読んでいない。

## 3. 決めること

各項目の「おすすめ」は今の時点の案。

### A. 名前

- Pak256-Ex と同じ `pak256` になる。遊ぶ人が混同し、配布サイトでも区別しにくい。
- **決定（2026-11-24、ユーザー）**: 表示名は `pak256.LongScale`、略称は `256LS`。縮尺（C）が名前で分かるようにして、Pak256-Ex と区別する。

### B. 権利の持ち方

ねらい（2026-11-24、ユーザー）: ゲームが非営利なので、お金をめぐる法的な争いは想定しない。作者が引退して連絡が取れなくなったとき、残った人が無断で直すことや名義を変えることをためらって、メンテが止まるのを防ぐ保険にする。他の作者のアドオンも pak セットに入れ、引退後も外さずにチームで直せるようにする。

**決定（2026-11-24、ユーザー）**: 絵と dat は **CC BY-SA 4.0** で出す。著作権は各作者が持ったまま。

CC BY-SA 4.0 で足りること（`https://creativecommons.org/licenses/by-sa/4.0/legalcode.en` を読んだ。法律の専門家には確かめていない）:

- 許諾は取り消せない（2(a)(1) の irrevocable、6(c)）。作者が引退しても、連絡が取れなくても、誰でも直して配れる。なので、権利の上での「共同管理」の取り決め（譲渡やチームとの契約）は要らない。
- 著作者人格権（同一性保持権など）は、直して配るのに必要な範囲で作者が行使しないと約束している（2(b)(1)）。
- 直した版でも元の作者の名前は残し、直したことを示す（3(a)(1)）。名義を差し替えることはできない。直した人の名前を足す形になる。作者から求められたときは名前を外す（3(a)(3)）。

許諾では足りず、運用の決まりとして書くこと（`CONTRIBUTING.md` などに置く）:

- 入れる条件: CC BY-SA 4.0 で出すことへの同意（PR のテンプレートで確認）と、元データ（Blender のファイル、dat を作る元の表）の提出。絵だけでは、許諾があっても直しにくい。
- クレジットの書き方: 元の作者名を残し、「改変: （直した人またはチーム）」を足す。
- 作者と連絡が取れないときの扱い: チームで直してよい、と先に書いておく。許諾の上では元から直せるが、直す人がためらわないように、また作者が入れるときに了承できるように明文にする。
- リポジトリは組織（`128-bit-net`）で持ち、管理者を複数にする。

素材の出どころ:

- 素材は新しく描く。pak128 の絵（Artistic License 2.0）を元にすると許諾が混ざるうえ、C で実物比例の縮尺に決めたので、pak128 の建物や車両は大きさが合わない。pak128 の絵を使うのは、4 章の試し（地面・GUI）だけにする。
- pak128.Japan の絵は、作者ごとの許諾が取れない限り使わない。
- **決定（2026-11-24、ユーザー）**: 道具のコード（dat を作るスクリプトなど）は **MIT** にする。CC は自らの FAQ でソフトウェアには勧めていない（ソースの扱い・特許の条項が無く、主なソフトウェアの許諾と混ぜにくい）。
- CC BY-SA は元データの公開を求めない（`.pak` だけを配っても許諾の上では問題ない）。元データを残すのは、上の「入れる条件」で担保する。

### C. 「タイルを 2 倍」の意味（縮尺）

- 案 1: 世界の縮尺は pak128 のまま、細かさだけ 2 倍にする。
- 案 2: 車両を実物の長さに比例させる（pak128.Japan と同じ考え方）。比例の決まりを規格に書く。
- 案 3: Pak256-Ex の縮尺に合わせる（Pak256-Ex の縮尺は未確認）。
- **決定（2026-11-24、ユーザー）**: 案 2。車両を実物の長さに比例させる。pak128 と pak128.Japan の車両の長さの違いを、規格の側で 1 つに決める。
- 引き受ける欠点: 車両は長く見える。本体は車両を 8 方向の絵でしか描かず、カーブで 22.5 度などの中間の向きが無いので、カーブで車両が線路からはみ出して見えるのが pak128 より目立つ。Simutrans はそういうゲームなので許容する。
- **決定（2026-11-24、ユーザー）**: 換算はまず pak128.Japan と同じ「実物の長さ（m）÷ 1.65」で試す。
- 車両の縮尺を決めると、建物・道路・木の大きさも決まる。車両だけの決まりにしない。

### D. 線路の描画位置

- 描画位置を 1 つにして、画素で決める（地面からレールの上面まで何 px、車輪の下端をどこに描くか）。線路・軌道・モノレールなど種類ごとに書く。
- 規格に合っているかを、見本の線路と車両を並べて撮る試験で確かめられるようにする。
- おすすめ（仮）: 新描画位置を 256px に直した値を基準にする（今ある pak128 の新しい線路と同じ見え方になる）。pak128・pak128.Japan の車両がどちらの位置に合わせて描かれているかは測っていないので、測ってから決める。

### E. 貨物の分類と旅客の等級

ここが pak128 と pak128.Japan のどちらに寄せるかの分かれ目になる。

- 案 1: pak128 の 7 分類と貨物の名前を使い、`Post` は郵便にする。
- 案 2: pak128.Japan の荷姿の分類と、一等・二等の旅客にする。
- **決定（2026-11-24、ユーザー）**: pak128 に寄せる。ただし pak128 と pak64 も違うように、pak128 と全く同じにする必要はない。`Post` は郵便にする。pak128.Japan から来る人には、一等・二等が無くなることを説明する。
- pak128 から変える所（足す貨物・分類、変える名前）は、産業の組み方を決めるときに一緒に決める。それまでは pak128 のままにする（2026-11-24、ユーザー）。

### F. 対象の本体

- おすすめ: 本家の最新版（今は 125.0.1）で動くことを条件にし、OTRP でも動かす（2.1 は OTRP のコードで読んだので、本家でも確かめる）。Extended は対象にしない（Pak256-Ex と分ける）。

### G. 「移行しやすい」の中身

- pak セットが違うと保存データは持ち越せない。なので移行しやすさは、名前・遊び方・値段の感覚が似ていることになる。
- どこまで似せるか（貨物の名前、産業のつながり、車両の顔ぶれ、値段の付け方）は決めていない。

### H. 作り方

- 絵は Blender の元データから描く。手元の道具（`simutrans-addon-dev` の `sheetlib`）の `CELL = 256` は pak128 の 2 タイル分の絵の大きさで、pak256 のことではない。タイルの大きさを引数にして描けるようにする。→ 倍率を 1 つ足せば、AMI の在来線を 256px のタイルで描けた（2026-11-24、[記録](records/2026-11-24_ami-rail-at-256.md)）。道具をどこに置くかは決めていない。
- dat は表（YAML など）から作り、CI で makeobj を回して pak を作る。

## 4. 最初の試し（案）

1. pak128 の基本の部分（地面・GUI・カーソル）を 2 倍に拡大し、`makeobj pak256` で pak にする。本体で起動するか、メモリと描画の速さを見る。→ 2026-11-24 に pak128 の全体で試し、起動とメモリを確かめた（[記録](records/2026-11-24_poc-upscale-pak128.md)）。描画の重さも小さな地図で測った。
2. 線路 1 種と車両 1 両を Blender から 256px で描き、描画位置の規格の試験の形を作る。→ 線路は AMI の在来線を流用して描き、地面と坂に合った（[記録](records/2026-11-24_ami-rail-at-256.md)）。車両はまだ。
3. 1・2 の結果で 2.1 の未確認を埋め、C の換算と D の数値を決める。2 の車両は、カーブでのはみ出し方も撮って見る。
